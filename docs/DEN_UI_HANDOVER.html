1. What The Den is

  • The Den is a single-owner, always-on service that runs on the user's Mac (formerly called claude-queue). Its product name is "Tushar's Workspace". The API runs at http://127.0.0.1:8787 and the dashboard at /dashboard.
  • Octopus is the nickname for the worker and the whole AI system: one brain (the router that decides which model handles a request) with many arms (Claude Code in any registered project, plus API models such as OpenAI and Gemini). The mascot is an octopus drawn in code with six moods.
  • Core loop: the user queues tasks per project. The Den runs them through Claude Code one at a time, moves to the next when one finishes, and resumes by itself after a usage limit.
  • Layers on top of the queue: Octopus request routing and planning; a personal assistant (email, calendar, reminders); voice and Alexa; a lightweight CRM and project-management layer (clients, contacts, activities, follow-ups, timeline, phases and autopilot); email and push notifications; documents, notes and a pad.
  • It lets the user trigger work from other devices (phone dashboard, SwiftBar, iOS Shortcuts, Alexa) instead of only from an editor.
  • Project plan: CRM [done]; Email notifications [done]; UI Setup [planned] — this document is the input for UI Setup.
  • Platform: phone first (bottom tab bar, swipe between pages, full-screen chat) with a sidebar layout from 900px up. The front end is plain ES modules with no build step. The older single-file dashboard still exists at /dashboard/legacy.

3. Access, auth and global behavior

  • One shared secret. Every API call sends X-API-Key. The page itself loads without auth but asks for the key on first visit and stores it in the browser's localStorage (cq_api_key). A wrong key shows "That key didn't work…" and clears it. Ten wrong keys from one address in a minute lock that address out (HTTP 429). The service refuses to start if HOST is not 127.0.0.1 and the key is empty.
  • No users and no roles. The only "roles" are a contact's key/stakeholder link on a project. There is no client portal: clients and contacts are records. The only thing a client ever receives is a Google Calendar invite.
  • Network: reachable over Tailscale; Web Push needs https (Tailscale Serve). Alexa needs a public path (Tailscale Funnel, only POST /alexa, verified by Amazon's signature).
  • Global scope switch: Work / Personal / All, which filters by project category. On phones it appears on the Projects page; on desktop at the top of the sidebar.
  • Polling: the dashboard refreshes every 5 seconds (skipped while the tab is hidden); a 1-second tick runs while anything is running, rate-limited or awaiting approval; a 30-second tick refreshes "2m ago" labels. Views patch the page in place so polling never interrupts typing.
  • Presence: while the tab is visible and was touched in the last few minutes, the page sends a heartbeat about every 20 seconds. After 90 seconds without one the owner counts as away, so Alexa can announce an approval instead. Held in memory only.
  • Credentials are never displayed: Claude tokens, OAuth tokens and API keys (only the last four characters of an API key) must never appear in the UI.

4. Processes (detailed workflows)

4.1 Task lifecycle (the heart of the app)

  1. Entry points: the Ask box on Home; the New task sheet (⌘K, N or the + button); a recipe; a schedule; a backlog item; voice; Alexa; the personal assistant; a phase autopilot tick; SwiftBar / iOS Shortcuts through the API.
  2. Queue. A new task goes after everything queued with the same or higher priority. The user can reorder by drag, move a task to the top, cancel it (with Undo), pause it (a queued task is skipped and keeps its place; a running Claude Code task is frozen and paused time does not count toward the timeout), play it, or stop it (kills the task and everything it launched).
  3. Run. One task at a time per Claude account, so projects on different accounts run side by side. Each tool call becomes a live step in the task's log (for example "Running npm test"). The same stream reports real 5-hour and weekly usage.
  4. Rate limit. The task shows "rate-limited" with a live countdown and resumes by itself at the reset time. "Retry now" is available. "Ping me when back" sends one push when a pause ends. "Save the session for urgent work" holds Low tasks while the 5-hour window is over 85%. A project pinned to a Claude account waits for that account and never moves to another.
  5. Sleep mode ("Going to sleep" on Home): the queue keeps going and uses limits fully; Low tasks are no longer held back; a limit with no reset time is retried every 15 minutes; approvals don't ping the phone and auto-deny after 5 minutes (the task is told to carry on without it). It ends after N hours (default 8, max 24) or when the user presses "I'm awake".
  6. Approvals (see 4.3) can pause a task mid-run.
  7. Finish: done (with an answer); needs_review (the user presses "Looks good" to mark it done); error (Retry, Open chat or Dismiss); cancelled.
  8. Chat. Every task is a conversation: all messages, Claude Code's step log, reply footers (status, model, time, cost) and a reply box. A reply resumes the same Claude session (thread_id). A reply can switch model (API models get the earlier messages, oldest dropped to fit the context window; Claude Code resumes its session plus a catch-up transcript). The choice sticks for later replies. A chat never changes kind midway.
  9. Other task actions: edit, retry-with-edit, run options (model, mode, priority, when), summarise (what was asked, what got done, where it stands; cached until the thread changes), transfer chat, move to another project, bulk move/priority/re-run/cancel/delete, delete to the recycle bin and restore, mark read/unread, requeue (front or back), "Retry now".
  10. Task detail page: plan steps, files changed, git branch and commits, tests seen, approvals, activity, result and the full diff.
  11. Titles: a quick name cut from the prompt shows at once, then the cheapest answer-only model replaces it with a 2–6 word title.
  12. Spend rules: "API spend" and budgets count real money only (OpenAI, Gemini). Claude Code cost is an estimate (a subscription does not bill it) and is shown on each task but not counted as spend. A project that reaches its monthly budget is paused and the owner gets a push.

4.2 Octopus: understand, plan, route, execute, validate, report

  1. Understand. Instant commands first (no model): "what's happening?", "stop the current task", "cancel that" (a waiting plan first), "continue the previous task", "list my projects", "add X to the backlog of Y". Then personal assistant, image, then a cheap classifier labels the request coding / general / simple (keyword rules are the backup).
  2. Plan (octopus/plan.py): project, agent (agents.json), model (scored), tools (tools.json), permissions, risk. Model choice weighs strength, cost, speed, track record and the user's configured order; scarce Claude Code usage is penalised for work that doesn't need it, more so when the 5-hour window is nearly used. Coding is non-transferable (it waits for Claude Code rather than hopping to a model with no project access). Every decision is stored with each candidate's score and shown on the Routing page.
  3. Review (optional). A plan card (the OCTOPUS PLAN) shows [Cancel] [Run]. Run may change project, model or agent first and only ever queues once. A plan is shown when it is risky, blocked, needs an answer, or the user chose "every request". "Don't change anything yet" in a request runs Claude Code in plan (read-only) mode.
  4. Execute in the lane: agent, api (text or image), assistant, or an instant command.
  5. Validate: tests seen in the run, files changed, git branch and diff.
  6. Report: text on the dashboard and a spoken line for voice.

Settings that shape it

  • Autonomy: Assist investigates and proposes (coding runs read-only); Execute runs normal actions and asks for risky ones; Autonomous also runs what would ask — but protected capabilities (deploy, force-push, delete, production, send email, admin) always ask unless the user sets them to Allow.
  • Plan preview: standard, every request, or only risky ones.
  • Agents (agents.json): instructions, preferred models, allowed tools and capabilities, context needs, execution policy (lane, when to show the plan, Claude Code mode per autonomy level, cost limit). Agents named in the product include the Creative Agent (images), Research (web-grounded), the Personal Assistant and the Voice Partner. Tools (tools.json): what a request needs; only those are given to a task (the rest are switched off for Claude Code); MCP servers can be added as "mcp" entries. Both are edited in Settings → Agents & tools and re-read on change with no restart.
  • Models (models.json): provider, capabilities, ratings, context, price, optimize mode per category (cost / balanced / quality), ordered candidates per category, vision flag, scarce flag. Models can be switched on/off and added/edited/removed from the AI Providers page (openai, gemini, claude_code).
  • Pictures: up to 6 per message (PNG/JPEG/GIF/WebP, 10 MB each). Routing picks only vision-capable models; Claude Code is told where the files are; API models receive real image parts.
  • Prompt polish: a "Polish" button rewrites a prompt using the cheapest answer-only model.
  • Image generation (gpt-image-1, gemini-image) saves pictures under workspace/images; Research uses web-search grounding.

4.3 Approval flow (Bash commands needing a human)

  1. Claude wants to run a command that unattended mode does not cover. A permission-prompt server writes a pending approval and the task waits.
  2. Where the user is told: a card in "Needs you" on Home; a toast and the notification panel; a phone push with Approve / Deny / Open dashboard buttons; the Dock/app badge count; and Alexa if the user has been away 90 seconds or more (not during sleep mode).
  3. The card shows: the command, a heuristic risk read with chips, the steps the task took before asking, and the project's uncommitted git diff.
  4. Decisions: Approve once; Always allow (adds the command to the project's allow list — an entry covers program plus subcommand, e.g. npm test; risky commands such as rm, sudo, curl, force-pushes and anything mentioning production are only allowed exactly as approved; commands that chain, pipe, redirect or substitute never match); Deny with an optional note that is passed back to Claude.
  5. Shortcuts: swipe right to approve and left to deny (110px threshold); A and D; Esc closes. The approval pane has a sticky "Approve once" (52px), "Always allow" and "Deny with a note".
  6. Link approval (from a push). The buttons are signed one-time links /approvals/{id}/quick/{approve|deny}?t=<token> (HMAC of the approval and the decision), because Safari cannot send the API key header. Tapping one opens a small standalone page with a title, a text line and the command in a code block, supporting dark mode and an "Open dashboard" link:
    • Approved ✓ (green accent): "Octopus is carrying on."
    • Denied (red accent): "Octopus won't run this and will work around it."
    • Link not valid (403): "This approval link is broken or was changed."
    • Not found (404): "That approval doesn't exist any more."
    • Already decided: says approved, denied, or closed (timed out or the task stopped).
  7. The service worker's Approve/Deny notification buttons call the same URLs and then show an "Approved ✓" or "Denied" notification.
  8. Timeout: unanswered approvals are denied after 1 hour (5 minutes in sleep mode) so the queue never stalls.
  9. Assistant approvals (email, calendar) are separate cards that run exactly what was shown, once; approvals unanswered for 24 hours expire; message content is dropped from the database after the decision. The assistant itself can never answer approvals, only count them.

4.4 Phases and autopilot

  1. The user splits a project into ordered phases (Phases tab) and puts to-dos in each; they can also move loose backlog items into a phase. AI task generation creates up to 15 to-dos for a phase using a chosen model.
  2. Start makes a phase active and queues its first open to-do immediately. Pause stops feeding the phase while queued/running work carries on. Complete closes it whatever is left. Reopen sets it back to planned. Reorder phases by drag.
  3. One to-do at a time: the next is queued only when the last finished. If one fails or needs review the phase stops and the owner gets a push — no more work piles on.
  4. What starts a phase (project autopilot mode): On my command (only on Start, or by saying "start the next phase of KodeAura7"); By the timeline (a phase starts on its start date, in order); When the limit allows (phases run back to back while Claude usage has room).
  5. Usage ceiling: default 85% of weekly usage (adjustable 10–100%) plus a fixed 90% cap on the 5-hour window. It holds automatic work until there is room; a phase the user starts by hand ignores it for its first item. The UI shows capacity/utilization.
  6. Every task for the project also sees the phase plan and the current phase's goal.
  7. The scheduler ticks every 30 seconds and returns pushes: started, done, blocked, late.
  8. Errors to design for: "That phase is already done."; "There's nothing to do in this phase yet - add some todos to it first."; a CRM-only project (no folder) can only plan phases, so Start/autopilot show a "no folder" hint.
  9. Voice: "start phase 2 of shop", "start the Build phase", "pause the phase of shop", "how are the phases going on shop".
  10. Progress report: a Markdown report for the whole project or chosen phases, with an optional model-written overview (POST /projects/{id}/report).

4.5 Backlog (to-dos) flow

  1. The Backlog is a per-project list separate from the queue. Add items by text (the composer says "Saving to backlog · won't run yet"), attach pictures, Polish text.
  2. Drag to order; star important items; expand a row to set model, approval mode, priority (Low/Normal/Urgent) or edit text.
  3. Tick items, then Run selected: they join the queue in the user's order (not selection order), each with its own model/mode/priority. The bar shows "N selected · joins after N tasks".
  4. A "Queue backlog in order" button also lives on the Work tab's Octopus card. The Suggest button queues a read-only review of the project and proposes tasks. Dragging a ticked row moves all ticked rows; drag is disabled while a row is expanded.

4.7 Follow-ups and reminders

  1. Add a follow-up to a project, client or contact with a date and optional time.
  2. At the due time (or 09:00 local if no time) a push goes out titled "Follow-up · <subject name>" with the message "<title> - due at 14:30 / due today / was due <day>". Tapping it opens that project overview, client or contact.
  3. A follow-up added or re-dated into the past is marked as already reminded (no instant push). Re-dating or reopening restarts its reminder.
  4. Follow-up reminders are held through quiet hours (23:00–08:00).
  5. Marking done stamps the time; reopening clears it. Done follow-ups appear struck through in the Calendar for 30 days.

4.9 Google Calendar invites (the only feature that emails outside people)

  1. Requires a connected Google account with Calendar (Personal → Connections). Without it the API returns 422: "Connect your Google account (with Calendar)…".
  2. In the meeting form the owner turns on Send invite and optionally Meet link. Only meetings can send invites.
  3. The Den saves the meeting, then creates the Google event on the primary calendar with all guests notified. Guests = contacts' CRM emails + extra guests. The meeting keeps the event id, invite link, Meet link and the Google account used.
  4. Google emails each guest the usual invitation with Accept and Decline. The repeat rule is translated to a Google recurrence rule.
  5. Editing (title, date, time, duration, guests, contacts, repeat) patches the event; guests get Google's update email; replies are preserved for guests who stay.
  6. Cancelling: the invite is cancelled (guests told) when "Send invite" is turned off, the meeting is cancelled, its kind changes away from meeting, or it is deleted. DELETE returns invite_cancelled, or a warning if Google cancel failed; the meeting is deleted anyway.
  7. Failures never lose the meeting. It is saved with an invite error (≤500 characters) shown under it; saving again retries. If the event was deleted in Google the error reads: 'The invite was deleted in Google Calendar. Turn on "Send invite" and save to send a new one.'
  8. UI states: none; sent; sent with a Meet link; error; contacts with no email.

4.10 Morning briefing

  • A "Good morning" page: greeting, date, today, overdue, upcoming (7 days), today's meetings (Google Calendar, if connected), approvals waiting, attention (failed or needs-review tasks from the last 7 days), reminders, queue counts, at-risk projects, plus a headline and text/spoken renderings.
  • Buttons: Read it to me, Refresh, Calendar. Shortcut G.
  • Pushed once a day at briefing_time (default 08:30) when briefing_push is on; tapping opens the briefing.
  • A built-in "Good morning" Quick button on Home runs it.

4.11 Notifications

Three channels

  1. ActivitySmith phone push. Levels vary by kind; urgent kinds (approval, failure, reminder) get high urgency and a 1-hour lifetime, others 24 hours. A push has a title, body (≤600 characters), kind, deep-link and optional approval id. Approvals and failures are time-sensitive (break through Focus); completions are a normal banner.
  2. Web Push to the dashboard installed as an app (Safari › Add to Dock, or iPhone Home Screen). Needs https. The VAPID key pair is created on first use. Subscriptions are per browser; a gone subscription is removed automatically. Approvals stay on screen until acted on; the Dock icon shows a red count of approvals waiting. A web app cannot bounce its Dock icon.
  3. Alexa: if an approval is waiting (or a task started from Alexa finishes) and the user has not used the dashboard for 90 seconds, the Echo lights up yellow. Only a count goes through Amazon's service; details are read by the skill. Nothing is sent while the user is on the dashboard, mid-conversation with the skill, or in sleep mode.

Push events

  • Approval needed; task failed; task done; message answered; rate-limit ended ("Ping me when back"); budget reached (project paused); follow-up due; timeline alerts (ahead, 60 minutes before, overdue); morning briefing; phase started, done, blocked or late; assistant reminders.

4.16 Backup, restore, restart, modules

  • Export tasks, history or settings as json or csv (anything that looks like a credential is stripped). Backup downloads the whole database (private).

  • Restart Octopus (Settings or the topbar): normal (waits for running tasks) or hard; native confirm. The page polls the service every 2 seconds and reloads when the process id changes. The offline popup is never shown during a restart. Email events cover the request and the result.

8. Open items, gaps and design brief

  • Design brief: build the complete Den UI from sections 2–7. Keep the phone-first approach and the 900px breakpoint, the dark theme with coral brand, mono-labelled dense cards, color reserved for status, and the Octopus mascot (six moods) in empty and error states. Keep the playful vs plain copy tones.
  • Pin-any-tab requirement (standing project note): any tab on the project page can be pinned. Current code only pins chat tabs. Design a pin affordance on every project tab (the ten tabs plus Settings), a clear pinned state, and where pinned tabs sit (suggested: first in the strip, kept across projects, persisted per device or per user setting).
  • Not built / thin: Outlook / Microsoft 365 (OAuth config exists; Graph adapters not built); local Whisper needs manual install; pictures on scheduled prompts; iOS Shortcuts flows (endpoints exist); Modules dashboard screen and command input; no client portal and no multi-user roles (by design today).
